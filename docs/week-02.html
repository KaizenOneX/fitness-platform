Git, properly

Do this first, before Docker. Every Docker iteration this week is a commit, and you want to understand what you're doing rather than pattern-matching commands. Both of us, ideally the same evening.

The mental modelBoth

Almost every confusing git moment comes from not knowing which of four places a change is sitting in:

Working directoryFiles as they are on disk right now
Staging areaChanges marked for the next commit — what git add does
Local repositoryCommitted history on your machine
RemoteGitHub's copy

Git tracks snapshots, not diffs. Every commit is a complete picture of the tree, and a branch is just a movable pointer at one of those snapshots. Once that lands, branching and merging stop feeling like magic.

Learn Git Branching — about two hoursBoth

learngitbranching.js.org — free, interactive, and it draws the commit graph as you manipulate it, which is exactly the model you want.

Do these, in order:

  • Main → Introduction Sequence — commits, branches, merge, rebase
  • Main → Ramping Up — HEAD, relative refs, reversing changes
  • Remote → Push & Pull — clone, fetch, pull, push, divergent history

Skip "Moving Work Around" and "Advanced Topics" for now. You'll want them around week 16 when you're cleaning up a messy extraction branch, not today.

The undo commandsBoth

This is the part most people never learn and most need. Learn the difference properly:

git restore file              # discard uncommitted changes to one file
git restore --staged file     # unstage, keep the changes
git reset --soft HEAD~1       # undo last commit, keep changes staged
git reset --mixed HEAD~1      # undo last commit, keep changes unstaged
git reset --hard HEAD~1       # undo last commit, DESTROY the changes
git revert abc1234            # new commit that undoes an old one
git reflog                    # every position HEAD has been in

--hard is the only one here that destroys work with no recovery path. It already cost us the bootstrap commit in week 1. --soft is almost always what you actually want. And revert rather than reset for anything already pushed — rewriting shared history breaks everyone else's clone.

git reflog is the safety net: it records every position HEAD has held, so even after a bad reset you can usually find the commit and git reset --hard <that-sha> back to it. Knowing it exists is what lets you experiment without fear.

Create a merge conflict on purposeBoth

Do this together, in the real repo, while the stakes are zero. A conflict is just two commits changing the same lines with no common ancestor to resolve it — it stops being frightening once you've caused one deliberately.

# both of you, from main
git switch main && git pull
git switch -c conflict-practice-YOURNAME

# both edit the SAME line of README.md, differently
git add README.md
git commit -m "test: conflict practice"
git push -u origin conflict-practice-YOURNAME

One of you merges first. The second person then rebases onto the updated main and resolves:

git switch main && git pull
git switch conflict-practice-YOURNAME
git rebase main
# git shows the conflict markers — edit the file, keep what you want
git add README.md
git rebase --continue

Then delete both branches. The point was the experience, not the change.

Docker, properly

Most people think they know Docker and carry three or four expensive misconceptions. Spend the week disproving that. Everything here is throwaway — it gets deleted in week 3 when the real scaffold arrives.

A trivial Go serviceBoth

In a scratch directory outside the repo, ~/scratch/dockerlab:

package main

import (
	"log/slog"
	"net/http"
	"os"
)

func main() {
	log := slog.New(slog.NewJSONHandler(os.Stdout, nil))

	mux := http.NewServeMux()
	mux.HandleFunc("GET /healthz", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte("ok"))
	})
	mux.HandleFunc("GET /", func(w http.ResponseWriter, r *http.Request) {
		log.Info("request", "path", r.URL.Path)
		w.Write([]byte("hello from the fitness platform\n"))
	})

	log.Info("listening", "addr", ":8080")
	http.ListenAndServe(":8080", mux)
}
cd ~/scratch/dockerlab
go mod init dockerlab
go run .

Note slog is standard library — structured JSON logging with no dependency. And "GET /healthz" as a route pattern is a Go 1.22+ feature: method and path in one string, which is why we're not adding a router library.

Build it the naive way, and measureBoth

FROM golang:1.25
WORKDIR /app
COPY . .
RUN go build -o server .
CMD ["./server"]
docker build -t lab:naive .
docker images lab:naive

Around 900 MB for a binary that's a few megabytes. The image contains the entire Go toolchain, the compiler, the standard library source — none of which is needed to run anything.

Multi-stage, and measure againBoth

FROM golang:1.25-alpine AS build
WORKDIR /src
COPY go.mod go.sum* ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/server .

FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=build /out/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]
docker build -t lab:multi .
docker images | grep lab

Around 10–15 MB. Roughly a 60× reduction. Four things did that:

  • Two stages — the toolchain stays in the build stage and never ships
  • CGO_ENABLED=0 — a fully static binary with no libc dependency, which is what makes distroless possible
  • -ldflags="-s -w" — strips the symbol table and debug info
  • distroless/static — no shell, no package manager, no OS utilities. Just a filesystem with your binary in it

That last point is a security property as much as a size one. There's no shell in the image, so an attacker who achieves code execution has nothing to pivot with.

Prove the layer cacheBoth

Change one line in main.go and rebuild. Watch which steps say CACHED.

docker build -t lab:multi .

The go mod download step should stay cached, because go.mod didn't change. That's why it's copied separately and before the rest of the source — dependencies change rarely, your code changes constantly, and the order of your COPY lines is what decides whether every build re-downloads the world.

Now try it wrong. Replace the two COPY lines with a single COPY . . before go mod download, change one line of source, rebuild, and watch the download run again.

This is the single most common Dockerfile mistake, and it turns a 5-second rebuild into a 60-second one. In week 6 with Tilt running, that difference is what makes the inner loop usable or miserable.

Inspect the layers directly:

docker history lab:multi

Everything in the build context gets sent to the Docker daemon before the build starts. Without this, .git alone can be tens of megabytes of pointless transfer on every build — and more importantly, anything in the context can end up in an image layer by accident.

Watch the "transferring context" line shrink after you add it.

Prove non-root actually tookBoth

docker run --rm lab:multi id

That fails — distroless has no id binary, or any shell. Which is the point. Check from outside instead:

docker run -d --name labtest -p 8080:8080 lab:multi
docker inspect labtest --format '{{.Config.User}}'
curl localhost:8080/healthz
docker rm -f labtest

You want nonroot:nonroot. In week 25 we apply Pod Security Standards at restricted, and images that already run non-root with a read-only root filesystem pass without argument. Static Go binaries on distroless make that nearly free — a payoff from this week's decision, six months later.

Scan itBoth

brew install trivy
trivy image lab:naive
trivy image lab:multi

The naive image has hundreds of CVEs from OS packages you never asked for. The distroless one has almost none, because there's almost nothing in it. That comparison is the argument for minimal base images in one screen.

gitleaks in CI and as a pre-commit hookManish

.github/workflows/gitleaks.yml:

name: gitleaks
on: [pull_request]

permissions:
  contents: read

jobs:
  scan:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: gitleaks/gitleaks-action@v2

Also install it locally, because CI catches a secret after it's already in history:

brew install gitleaks pre-commit
cd ~/projects/fitness-platform
cat > .pre-commit-config.yaml <<'EOF'
repos:
  - repo: https://github.com/gitleaks/gitleaks
    rev: v8.21.2
    hooks:
      - id: gitleaks
EOF
pre-commit install

That permissions: block matters more than it looks. By default a workflow token gets broad write access. Setting contents: read at the top of every workflow and granting more only per-job is the single highest-value Actions hardening step, and almost nobody does it.

Architecture decision records

The templateBoth

# ADR-0001: Backend language

- Status: accepted
- Date: 2026-09-XX
- Deciders: Manish, Jigar

## Context

What forces are at play? What constraints matter?

## Decision

What we're doing.

## Consequences

The "Alternatives considered" section is the one that pays off. In four months when someone suggests switching, that section tells you whether it's a new idea or one you already rejected for a reason.

Reference

If something goes wrong
docker build fails on go.sum
A project with no dependencies has no go.sum. The go.sum* glob in the COPY line handles that — if you typed go.sum exactly, the build fails on a missing file.
Image is much bigger than 15 MB
Check CGO_ENABLED=0 is set. Without it the binary links against libc and won't run on distroless/static at all.
"exec /server: no such file or directory" on run
Same cause — a dynamically linked binary in an image with no dynamic linker. The error is misleading; the file is there.
go mod download re-runs on every build
Your COPY ordering is wrong. go.mod must be copied and downloaded before the rest of the source.
pre-commit hook doesn't fire
pre-commit install has to run inside the repo, once per clone. It writes to .git/hooks/, which isn't tracked.
Rebase conflict you can't untangle
git rebase --abort puts everything back. Nothing is lost. Then try git merge main instead — messier history, simpler resolution.
